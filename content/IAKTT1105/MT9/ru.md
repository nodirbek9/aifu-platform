## Масштабирование

| Способ | Содержание | Ограничение |
|---|---|---|
| **Вертикальное** (scale up) | усиление одного сервера: больше процессоров, памяти | дорого, есть физический предел, один сбой — всё останавливается |
| **Горизонтальное** (scale out) | объединение множества обычных серверов в кластер | задачу нужно делить, а результаты собирать |

Технологии Big Data основаны на горизонтальном масштабировании: данные и вычисления распределяются по узлам кластера, а если один узел выходит из строя, его работу выполняет другой (есть копии данных).

## Парадигма MapReduce

Модель, предложенная Google (2004) и реализованная в Hadoop. Задача делится на две простые функции:

1. **Map** — каждый узел читает свою часть данных и выдаёт пары (ключ, значение): (регион, сумма).
2. **Combine** (необязательно) — предварительно суммирует одинаковые ключи внутри узла — по сети передаётся меньше данных.
3. **Shuffle** — пары с одинаковым ключом отправляются одному «reducer».
4. **Reduce** — итоговый результат по каждому ключу: сумма, количество, максимум.

Главная идея: **приближать вычисления к данным**. Вместо копирования терабайтов на один сервер каждый узел сам обрабатывает часть на своём диске.

## Разобранный пример: моделирование MapReduce

Записи о продажах (регион, сумма в млн сумов) распределяются равными частями по 3 узлам. Каждый узел выполняет map и combine, затем reduce даёт итоговую сумму. Это распределённый вариант SQL-конструкции `GROUP BY регион` (M7).

```python
import sys

TUGUNLAR = 3

satrlar = [s for s in sys.stdin.read().split("\n") if s.strip()]
qism = (len(satrlar) + TUGUNLAR - 1) // TUGUNLAR

# этап 1: Map + Combine — каждый узел обрабатывает свою часть
oraliq = []
for t in range(TUGUNLAR):
    mahalliy = {}
    for satr in satrlar[t * qism:(t + 1) * qism]:
        hudud, summa = satr.split()
        mahalliy[hudud] = mahalliy.get(hudud, 0) + int(summa)
    oraliq.append(mahalliy)
    juftlar = ", ".join(f"{k}={mahalliy[k]}" for k in sorted(mahalliy))
    print(f"Узел {t + 1}: {juftlar}")

# этап 2: Shuffle — одинаковые ключи собираются у одного reducer
# этап 3: Reduce — итоговая сумма
jami = {}
for mahalliy in oraliq:
    for k, v in mahalliy.items():
        jami[k] = jami.get(k, 0) + v
for k in sorted(jami):
    print(f"Итого {k}: {jami[k]}")
```
```java
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.Scanner;
import java.util.TreeMap;

public class Main {
    static final int TUGUNLAR = 3;

    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        List<String> satrlar = new ArrayList<>();
        while (in.hasNextLine()) {
            String s = in.nextLine();
            if (!s.isBlank()) satrlar.add(s.trim());
        }
        int qism = (satrlar.size() + TUGUNLAR - 1) / TUGUNLAR;

        // этап 1: Map + Combine — каждый узел обрабатывает свою часть
        List<TreeMap<String, Long>> oraliq = new ArrayList<>();
        for (int t = 0; t < TUGUNLAR; t++) {
            TreeMap<String, Long> mahalliy = new TreeMap<>();
            for (int i = t * qism; i < Math.min((t + 1) * qism, satrlar.size()); i++) {
                String[] q = satrlar.get(i).split("\\s+");
                mahalliy.merge(q[0], Long.parseLong(q[1]), Long::sum);
            }
            oraliq.add(mahalliy);
            List<String> juftlar = new ArrayList<>();
            for (Map.Entry<String, Long> e : mahalliy.entrySet()) juftlar.add(e.getKey() + "=" + e.getValue());
            System.out.println("Узел " + (t + 1) + ": " + String.join(", ", juftlar));
        }

        // этап 2: Shuffle — одинаковые ключи собираются у одного reducer
        // этап 3: Reduce — итоговая сумма
        TreeMap<String, Long> jami = new TreeMap<>();
        for (TreeMap<String, Long> mahalliy : oraliq)
            for (Map.Entry<String, Long> e : mahalliy.entrySet()) jami.merge(e.getKey(), e.getValue(), Long::sum);
        for (Map.Entry<String, Long> e : jami.entrySet())
            System.out.println("Итого " + e.getKey() + ": " + e.getValue());
    }
}
```
```cpp
#include <iostream>
#include <map>
#include <sstream>
#include <string>
#include <vector>
using namespace std;

const int TUGUNLAR = 3;

int main() {
    vector<string> satrlar;
    string s;
    while (getline(cin, s))
        if (s.find_first_not_of(" \t\r") != string::npos) satrlar.push_back(s);
    int n = satrlar.size();
    int qism = (n + TUGUNLAR - 1) / TUGUNLAR;

    // этап 1: Map + Combine — каждый узел обрабатывает свою часть
    vector<map<string, long long>> oraliq;
    for (int t = 0; t < TUGUNLAR; t++) {
        map<string, long long> mahalliy;
        for (int i = t * qism; i < min((t + 1) * qism, n); i++) {
            istringstream ss(satrlar[i]);
            string hudud;
            long long summa;
            ss >> hudud >> summa;
            mahalliy[hudud] += summa;
        }
        oraliq.push_back(mahalliy);
        cout << "Узел " << t + 1 << ": ";
        bool birinchi = true;
        for (auto& [k, v] : mahalliy) {
            cout << (birinchi ? "" : ", ") << k << "=" << v;
            birinchi = false;
        }
        cout << "\n";
    }

    // этап 2: Shuffle — одинаковые ключи собираются у одного reducer
    // этап 3: Reduce — итоговая сумма
    map<string, long long> jami;
    for (auto& mahalliy : oraliq)
        for (auto& [k, v] : mahalliy) jami[k] += v;
    for (auto& [k, v] : jami) cout << "Итого " << k << ": " << v << "\n";
    return 0;
}
```

Благодаря combine узел 1 отправляет reducer 2 пары вместо 3 записей. На миллиардах записей это в разы сокращает сетевой трафик. В реальном кластере узлы работают параллельно: 1 000 узлов обрабатывают данные примерно в 1 000 раз быстрее (часть выигрыша уходит на сеть и координацию).

## Apache Spark

Hadoop MapReduce записывает результат каждого этапа на диск — это медленно. **Spark** хранит промежуточные результаты **в оперативной памяти** и в многоэтапном анализе (например, когда машинное обучение многократно проходит по одним и тем же данным) работает в десятки раз быстрее. **«Ленивое» выполнение**: Spark не выполняет команды сразу, а сначала строит и оптимизирует весь план и вычисляет, только когда запрошен результат. Spark поддерживает SQL, Python (PySpark), машинное обучение (MLlib) и потоки.

## Потоковая обработка

Данные платежей, касс, датчиков поступают непрерывно. Потоковые системы (Kafka + Spark Streaming или Flink) обрабатывают их по мере поступления. Ключевое понятие — **временное окно**:

| Вид окна | Пример |
|---|---|
| **Фиксированное** (tumbling) | сумма продаж каждые 5 минут: 10:00–10:05, 10:05–10:10 |
| **Скользящее** (sliding) | сумма за последний час, обновляется каждую минуту |
| **Сеансовое** (session) | одно посещение сайта пользователем (до перерыва в активности) |

Правило подозрительной транзакции из S7 работает именно на таком потоке.

## ETL и ELT

| Процесс | Порядок | Когда |
|---|---|---|
| **ETL** (Extract — Transform — Load) | извлечь из источника → очистить и преобразовать → загрузить в хранилище | традиционные хранилища данных, строгая структура |
| **ELT** (Extract — Load — Transform) | загрузить в сыром виде → преобразовать внутри хранилища при необходимости | облачные хранилища и озёра данных, большие объёмы |

## Хранилище, озеро и lakehouse

- **Хранилище данных** (data warehouse) — очищенные структурированные данные для отчётов (SQL).
- **Озеро данных** (data lake) — сырые данные любого формата, хранящиеся дёшево (файлы, логи, изображения).
- **Lakehouse** — дешевизна озера и порядок хранилища вместе.

Слои **бронза — серебро — золото**:

| Слой | Содержание | Пример |
|---|---|---|
| **Бронза** | сырые неизменённые данные | чеки с касс в виде JSON |
| **Серебро** | очищенные, объединённые, без дубликатов | таблица продаж в едином формате |
| **Золото** | готовые для бизнеса агрегаты | выручка по регионам и дням, для дашбордов |

## Качество данных

| Измерение | Вопрос | Пример нарушения |
|---|---|---|
| **Полнота** | все ли нужные значения есть? | у 15% клиентов нет телефона |
| **Точность** | соответствует ли значение действительности? | цена 850 000 вместо 85 000 |
| **Согласованность** | одинаково ли в разных системах? | адрес клиента в CRM и бухгалтерии разный |
| **Своевременность** | свежие ли данные? | отчёт на данных прошлой недели, а не вчерашних |
| **Уникальность** | нет ли дубликатов? | один клиент записан трижды в разном написании |
| **Валидность** | соответствует ли формату и правилам? | дата «31.02.2025» |

## Затраты на аналитику в облаке

Облачные сервисы Big Data (BigQuery, Snowflake, Databricks и др.) часто берут плату за **объём просканированных данных** или **время вычислений**. Поэтому: запрашивайте только нужные столбцы (не `SELECT *`), разбивайте таблицы по дате (партиционирование), используйте готовые агрегаты золотого слоя, отключайте неиспользуемые кластеры (FinOps, S11).

:::warning
**Частые ошибки**

- **Технологии Big Data для небольших данных.** Для нескольких ГБ достаточно Excel, Python или обычной СУБД — и это дешевле.
- **Отдавать в отчёт сырые данные без очистки.** Проверяйте измерения качества.
- **Превращать озеро в «болото».** Без метаданных (что, откуда, когда) данные никто не найдёт.
- **Не контролировать затраты.** Один неверный запрос может просканировать терабайты и принести большой счёт.
:::

## Итоги

- Big Data основана на горизонтальном масштабировании: вычисления приближаются к данным.
- MapReduce: map → combine → shuffle → reduce; Spark работает в памяти и быстрее.
- Потоковая обработка работает с временными окнами; ETL/ELT доставляет данные в хранилище.
- Архитектура: хранилище, озеро, lakehouse; бронза → серебро → золото.
- Качество данных оценивается по шести измерениям; облачные затраты контролируются.
