## Почему это важно

IP доставляет пакет **компьютеру**. Но на компьютере одновременно работают браузер, мессенджер, музыкальное приложение и служба обновлений — **какой программе** принадлежат пришедшие данные? Кроме того, IP-пакет может потеряться или прийти не по порядку, а файл должен прийти правильным до последнего байта. Эти две задачи решает **транспортный уровень**: **порты** определяют программу, а **TCP** обеспечивает надёжную доставку. Каждая сетевая программа обращается к транспортному уровню через **сокет**.

## Функции транспортного уровня

| Функция | Смысл |
|---|---|
| **Доставка между процессами** | IP — от компьютера к компьютеру, транспорт — от программы к программе |
| **Мультиплексирование** | многие программы одновременно используют один IP-адрес; их различают по номеру **порта** |
| **Сегментация** | деление большого потока данных на сегменты и обратная сборка |
| **Надёжность** (TCP) | повторная отправка потерянного, удаление дубликатов, восстановление порядка |
| **Управление потоком** (TCP) | быстрый отправитель не должен «завалить» медленного получателя |
| **Управление перегрузкой** (TCP) | снижение скорости при загрузке сети |

**Порт** — 16-битное число (0–65 535): 0–1023 — **общеизвестные** (well-known) порты, 1024–49 151 — зарегистрированные, 49 152–65 535 — **временные** (ephemeral) порты, ОС выдаёт их автоматически для клиентских соединений.

| Порт | Протокол | Порт | Протокол |
|---|---|---|---|
| 20, 21 | FTP | 80 | HTTP |
| 22 | SSH | 110 / 143 | POP3 / IMAP |
| 23 | Telnet | 443 | HTTPS |
| 25 | SMTP | 3389 | RDP |
| 53 | DNS (UDP и TCP) | 67, 68 | DHCP (UDP) |

Каждое TCP-соединение определяется **пятёркой** (5-tuple): протокол, IP и порт источника, IP и порт получателя. Поэтому к порту 443 одного веб-сервера одновременно могут подключиться тысячи клиентов — у них различаются IP или порт.

## UDP

**UDP** (User Datagram Protocol) — минимальный транспорт: заголовок всего **8 байт** (порт источника, порт получателя, длина, контрольная сумма). Соединение не устанавливается, подтверждений и повторной передачи нет, порядок не гарантируется. Преимущество — **скорость и малая задержка**. Применение: запросы DNS, онлайн-игры, голосовые и видеозвонки (потерянный пакет лучше опоздавшего), DHCP, IPTV multicast. Современный **QUIC** (HTTP/3) сам строит надёжность поверх UDP.

## TCP

**TCP** (Transmission Control Protocol) — надёжный, упорядоченный **поток байтов** с установлением соединения. Заголовок — не менее **20 байт**:

| Поле | Смысл |
|---|---|
| Порты источника и получателя | 16 + 16 бит |
| **Порядковый номер** (Sequence) | номер первого байта сегмента в потоке |
| **Номер подтверждения** (Acknowledgment) | номер **следующего ожидаемого** получателем байта |
| Длина заголовка | в 4-байтных словах |
| Флаги | **SYN** (соединение), **ACK** (поле подтверждения действительно), **FIN** (закрытие), **RST** (сброс), PSH, URG |
| **Окно** (Window) | сколько ещё байтов может принять получатель (управление потоком) |
| Контрольная сумма | для заголовка и данных |

### Трёхэтапное установление соединения (three-way handshake)

1. Клиент → сервер: **SYN**, seq = *x* (случайный начальный номер, ISN).
2. Сервер → клиент: **SYN+ACK**, seq = *y*, ack = *x* + 1.
3. Клиент → сервер: **ACK**, seq = *x* + 1, ack = *y* + 1.

Флаги SYN и FIN занимают по одному «виртуальному байту» — поэтому подтверждение +1. После этого передаются данные: если пришёл сегмент из *L* байт с seq = *s*, получатель отвечает ack = *s* + *L*.

**Закрытие** — в четыре шага (каждая сторона отправляет FIN, другая возвращает ACK). Сторона, закрывшая активно, ждёт 2×MSL в состоянии **TIME_WAIT**, чтобы запоздавшие сегменты не попали в новое соединение. Основные состояния: LISTEN, SYN_SENT, SYN_RECEIVED, ESTABLISHED, FIN_WAIT, CLOSE_WAIT, TIME_WAIT, CLOSED (видны в `netstat -an`).

### Надёжность, окно и перегрузка

- **Повторная передача**: если подтверждение не пришло до истечения таймера (RTO), сегмент отправляется снова; при трёх дублирующих ACK — сразу (**fast retransmit**).
- **Скользящее окно**: отправитель может отправить до размера окна байтов, не дожидаясь подтверждений. Поэтому скорость одного соединения ≤ окно / RTT. Чтобы полностью загрузить сеть, окно должно быть не меньше **BDP** (bandwidth-delay product = скорость × RTT); для окон больше 64 КБ есть опция **window scaling**.
- **Управление перегрузкой**: отправитель ведёт дополнительное окно **cwnd** — **медленный старт** (slow start, удвоение каждый RTT), затем **AIMD** (+1 сегмент за RTT, при потере — вдвое меньше). Действующее окно = min(cwnd, окно получателя).

## TCP и UDP

| | TCP | UDP |
|---|---|---|
| Соединение | есть (handshake) | нет |
| Надёжность | подтверждения и повторная передача | нет |
| Порядок | восстанавливается | не гарантируется |
| Заголовок | 20–60 байт | 8 байт |
| Управление потоком/перегрузкой | есть | нет |
| Данные | поток байтов | отдельные сообщения (датаграммы) |
| Применение | веб, почта, файлы, SSH | DNS, голос/видео, игры, DHCP |

## Сокеты

**Сокет** — **программный интерфейс** (API) между программой и транспортным уровнем; «конец» сетевого соединения в программе. Определяется IP-адресом, портом и протоколом. API сокетов появился в BSD Unix в 1983 году и сейчас почти одинаков во всех языках:

```text
TCP-сервер                         TCP-клиент
socket()   создать сокет           socket()
bind()     привязать к IP:port
listen()   ждать соединений
accept()   принять соединение  <—  connect()   (трёхэтапное соединение)
recv()/send()                      send()/recv()
close()                            close()

UDP: socket() → bind() (сервер) → sendto()/recvfrom() → close()   (без соединения)
```

`accept()` для каждого клиента возвращает **новый** сокет, а слушающий сокет продолжает ждать следующих клиентов. Практическая программа с сокетами — на занятии A9.

## Разобранный пример 1: порядковые номера и подтверждения

В первой строке — начальные порядковые номера (ISN) клиента и сервера. В следующих строках — кто отправляет (`C` — клиент, `S` — сервер) и длина данных. Выведите трёхэтапное установление соединения, затем каждый сегмент данных и ответный ACK другой стороны. Ввод читается до конца файла.

```python
import sys

satrlar = sys.stdin.read().split("\n")
c_seq, s_seq = map(int, satrlar[0].split())
print("C->S SYN seq=" + str(c_seq))
print("S->C SYN+ACK seq=" + str(s_seq) + " ack=" + str(c_seq + 1))
c_seq += 1                                   # SYN занимает один номер
s_seq += 1
print("C->S ACK seq=" + str(c_seq) + " ack=" + str(s_seq))
for satr in satrlar[1:]:
    if not satr.strip():
        continue
    kim, uzunlik = satr.split()
    uzunlik = int(uzunlik)
    if kim == "C":
        print("C->S seq=" + str(c_seq) + " ack=" + str(s_seq) + " len=" + str(uzunlik))
        c_seq += uzunlik
        print("S->C ACK seq=" + str(s_seq) + " ack=" + str(c_seq))   # следующий ожидаемый байт
    else:
        print("S->C seq=" + str(s_seq) + " ack=" + str(c_seq) + " len=" + str(uzunlik))
        s_seq += uzunlik
        print("C->S ACK seq=" + str(c_seq) + " ack=" + str(s_seq))
```
```java
import java.util.Scanner;

public class Main {
    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        long cSeq = in.nextLong();
        long sSeq = in.nextLong();
        System.out.println("C->S SYN seq=" + cSeq);
        System.out.println("S->C SYN+ACK seq=" + sSeq + " ack=" + (cSeq + 1));
        cSeq += 1;                                            // SYN занимает один номер
        sSeq += 1;
        System.out.println("C->S ACK seq=" + cSeq + " ack=" + sSeq);
        while (in.hasNext()) {
            String kim = in.next();
            long uzunlik = in.nextLong();
            if (kim.equals("C")) {
                System.out.println("C->S seq=" + cSeq + " ack=" + sSeq + " len=" + uzunlik);
                cSeq += uzunlik;
                System.out.println("S->C ACK seq=" + sSeq + " ack=" + cSeq);   // следующий ожидаемый байт
            } else {
                System.out.println("S->C seq=" + sSeq + " ack=" + cSeq + " len=" + uzunlik);
                sSeq += uzunlik;
                System.out.println("C->S ACK seq=" + cSeq + " ack=" + sSeq);
            }
        }
    }
}
```


## Разобранный пример 2: окно и предел скорости

В каждой строке — окно TCP (байт), RTT (мс) и скорость канала (Мбит/с). Выведите наибольшую скорость одного соединения (Мбит/с, два знака; меньшее из окно/RTT и скорости канала) и окно, нужное для полной загрузки канала, — BDP (байт).

```python
import sys

for satr in sys.stdin:
    if not satr.strip():
        continue
    oyna, rtt, kanal = map(int, satr.split())
    oyna_tezligi = oyna * 8 / (rtt / 1000) / 1_000_000    # Mbit/s
    tezlik = min(oyna_tezligi, kanal)
    bdp = kanal * rtt * 125                               # Мбит/с * мс -> байты
    print(f"{tezlik:.2f} Mbit/s BDP={bdp}")
```
```java
import java.util.Scanner;

public class Main {
    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        while (in.hasNextLong()) {
            long oyna = in.nextLong();
            long rtt = in.nextLong();
            long kanal = in.nextLong();
            double oynaTezligi = oyna * 8 / (rtt / 1000.0) / 1_000_000;   // Mbit/s
            double tezlik = Math.min(oynaTezligi, kanal);
            long bdp = kanal * rtt * 125;                                // Мбит/с * мс -> байты
            System.out.println(String.format("%.2f", tezlik) + " Mbit/s BDP=" + bdp);
        }
    }
}
```
```cpp
#include <algorithm>
#include <cstdio>
#include <iostream>
using namespace std;

int main() {
    long long oyna, rtt, kanal;
    while (cin >> oyna >> rtt >> kanal) {
        double oynaTezligi = oyna * 8 / (rtt / 1000.0) / 1000000;      // Mbit/s
        double tezlik = min(oynaTezligi, (double) kanal);
        long long bdp = kanal * rtt * 125;                             // Мбит/с * мс -> байты
        printf("%.2f Mbit/s BDP=%lld\n", tezlik, bdp);
    }
    return 0;
}
```

Ввод:

```text
65535 50 100
1048576 50 100
65535 1 1000
```

Вывод:

```text
10.49 Mbit/s BDP=625000
100.00 Mbit/s BDP=625000
524.28 Mbit/s BDP=125000
```

Первая строка — классическая проблема: канал 100 Мбит/с, но с окном 64 КБ и RTT 50 мс соединение получает лишь ~10 Мбит/с; нужно окно 625 000 байт (≈ 610 КБ). Поэтому загрузка с далёкого сервера может быть медленной даже по быстрому каналу — если не включено масштабирование окна.

:::warning
**Частые ошибки**

- **Думать, что номер подтверждения — последний принятый байт.** ACK — номер **следующего ожидаемого** байта.
- **Считать SYN и FIN «пустыми».** Каждый занимает один порядковый номер — поэтому после handshake seq + 1.
- **Понимать UDP как «плохой TCP».** Для приложений реального времени повторная передача вредна: опоздавший голосовой пакет не нужен.
- **Считать порт и сокет одним и тем же.** Порт — число; сокет — программная точка соединения, определяемая IP, портом и протоколом.
- **Думать, что скорость зависит только от канала.** Одно TCP-соединение не может работать быстрее окно/RTT.
:::

:::tip
Откройте в браузере несколько сайтов и выполните в командной строке `netstat -an | findstr ESTABLISHED` (Linux: `ss -tn`): в каждой строке видны локальный IP:порт (временный порт) и удалённый IP:443. Это ваши открытые TCP-соединения.
:::

## Итоги

- Транспортный уровень доставляет от программы к программе; программы различаются портами; соединение определяется пятёркой.
- UDP: заголовок 8 байт, без соединения, без гарантий, быстрый — DNS, голос, игры.
- TCP: трёхэтапное соединение, seq/ack, повторная передача, скользящее окно, управление потоком и перегрузкой, закрытие в четыре шага.
- Скорость одного TCP-соединения ≤ окно / RTT; для полной загрузки канала окно ≥ BDP.
- Сокет — точка входа программы в сеть: сервер socket–bind–listen–accept, клиент socket–connect.

## Проверьте себя

:::check
Q: Клиент отправил в SYN seq = 300. Какой ack вернёт сервер в SYN+ACK?
A: ack = 301 — SYN занимает один порядковый номер.
Q: Принят сегмент с seq = 2000 и 500 байтами данных. Каков номер подтверждения в ответном ACK?
A: 2500 — следующий ожидаемый байт.
Q: Почему запросы DNS обычно отправляются по UDP?
A: Запрос и ответ малы, установление соединения добавило бы лишнюю задержку; при потере клиент просто повторит запрос.
Q: Окно 32 КБ, RTT 100 мс. Какова наибольшая скорость одного соединения?
A: 32 768 × 8 / 0,1 ≈ 2,6 Мбит/с.
Q: Что возвращает `accept()` на сервере?
A: Новый сокет для работы с принятым клиентом; слушающий сокет продолжает ждать следующих соединений.
