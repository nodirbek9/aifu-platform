## Почему это важно

До сих пор вы, возможно, писали программы в простом текстовом редакторе и компилировали их из командной строки. Для маленьких программ этого достаточно. Но когда программа дорастает до сотен строк и результат выходит неверным, поиск ответа на вопрос «где ошибка?» расстановкой `print` может занять часы.

**Интегрированная среда разработки** (IDE) объединяет в одном окне редактор, компилятор и **отладчик** (debugger). Отладчик останавливает программу на любой строке, показывает значения всех переменных и позволяет выполнять программу по шагам. Профессиональные программисты проводят значительную часть времени именно в отладчике. На этой лекции изучим эти инструменты на примере Visual Studio; в IntelliJ IDEA, PyCharm и VS Code они почти такие же.

:::note
**После этого занятия вы сможете:**

- называть основные части IDE и их назначение;
- создавать в Visual Studio решение и проект, собирать и запускать программу на C++;
- объяснять разницу между конфигурациями Debug и Release;
- ставить точку останова, выполнять программу по шагам и следить за переменными;
- систематически искать ошибку — гипотеза, проверка, исправление.
:::

## Состав IDE

| Часть | Назначение | В Visual Studio |
|---|---|---|
| Редактор | написание кода, подсветка, автодополнение | IntelliSense — при наборе имени появляются подсказки |
| Система проектов | хранит, какие файлы входят в программу и как она собирается | окно Solution Explorer |
| Сборщик (build) | вызывает компилятор и компоновщик (linker) | Build → Build Solution (Ctrl+Shift+B) |
| Список ошибок | ошибки и предупреждения компилятора | окно Error List (двойной щелчок по ошибке переходит к строке) |
| Отладчик | остановка программы, шаги, просмотр значений | меню Debug, окна Locals, Watch, Call Stack |

## Решение и проект

В Visual Studio работа организуется внутри **решения** (solution, файл `.sln`). Решение состоит из одного или нескольких **проектов** (project, для C++ — `.vcxproj`); каждый проект даёт одну программу или библиотеку.

Создание новой программы на C++:

1. File → New → Project → выберите шаблон **Console App** (C++).
2. Введите имя и расположение проекта → Create.
3. В Solution Explorer в `Source Files` появится файл `.cpp` — здесь вы пишете код.
4. Ctrl+F5 — запуск без отладчика (окно не закрывается после завершения программы), F5 — с отладчиком.

Выбор стандарта C++: правый щелчок по проекту → Properties → C/C++ → Language → **C++ Language Standard** (например, ISO C++17). Уровень предупреждений: C/C++ → General → **Warning Level** — для учебных программ рекомендуется `/W4`.

## Debug и Release

| | Debug | Release |
|---|---|---|
| Назначение | поиск ошибок | версия для пользователей |
| Оптимизация | нет — код выполняется как написан | включена — компилятор переупорядочивает код |
| Отладочная информация | полная — видна каждая строка и переменная | минимальная |
| `assert` | работает | отключается (определяется `NDEBUG`) |
| Скорость | медленнее | может быть в несколько раз быстрее |

Конфигурация выбирается из списка на панели инструментов. Важный урок: некоторые ошибки (например, переменная без начального значения) могут «работать» в Debug и давать другой результат в Release — программу проверяют в обоих режимах.

## Работа с отладчиком

**Точка останова** (breakpoint) — метка, на которой программа останавливается, дойдя до этой строки. Её ставят щелчком по левому полю строки или клавишей F9; она показывается красным кружком. Когда программа остановилась:

| Действие | Visual Studio / VS Code | IntelliJ IDEA / PyCharm |
|---|---|---|
| Запуск с отладчиком | F5 | Shift+F9 |
| Поставить/снять точку останова | F9 | Ctrl+F8 |
| К следующей строке (не заходя в функции) — Step Over | F10 | F8 |
| Зайти в функцию — Step Into | F11 | F7 |
| Выйти из функции — Step Out | Shift+F11 | Shift+F8 |
| Продолжить до следующей точки останова | F5 | F9 |

Полезные окна во время остановки:

- **Locals** (Variables) — все переменные текущей функции и их значения;
- **Watch** — добавленные вами выражения (например, `a[i] + a[j]`, `yigindi / n`), пересчитываются на каждом шаге;
- **Call Stack** — какая функция какую вызвала; очень полезно, чтобы видеть цепочку вызовов в рекурсии;
- **Условная точка останова** — правый щелчок по точке → Conditions: например, остановиться при `i == 500`. В больших циклах избавляет от тысячи нажатий F5.

## Систематический поиск ошибки

Отладчик — инструмент; поиск ошибки — **метод**. Эффективный порядок:

1. **Воспроизведите.** Найдите наименьший ввод, который каждый раз вызывает ошибку.
2. **Вычислите ожидаемый результат вручную.** Что программа *должна* вывести?
3. **Выдвиньте гипотезу.** Какая часть может работать неверно?
4. **Проверьте.** Поставьте там точку останова и сравните переменные с ожидаемыми значениями. Найдите строку, где значение впервые «портится».
5. **Исправьте и проверьте снова** — вместе со всеми прежними тестами.

Если поставить точку останова нельзя (например, в системе автоматической проверки), отладочную информацию выводят в **поток ошибок**: `cerr` (C++), `System.err` (Java), `sys.stderr` (Python). Этот поток не смешивается с основным выводом, и тесты его не проверяют.

## Разобранный пример 1: ошибка в среднем значении

Задача: даны *n* и *n* целых чисел; вывести среднее арифметическое с двумя знаками после запятой. Студент написал такой код на C++ и получил `1.00` для `3` и `1 2 2`, хотя ответ должен быть `1.67`:

```text
int yigindi = 0;
for (int i = 0; i < n; i++) yigindi += a[i];
double ortacha = yigindi / n;          // ← точка останова на этой строке
printf("%.2f\n", ortacha);
```

Остановившись на этой строке в отладчике, добавляем выражения в окно Watch:

| Выражение | Значение | Вывод |
|---|---|---|
| `yigindi` | 5 | верно |
| `n` | 3 | верно |
| `yigindi / n` | 1 | **ошибка здесь**: оба операнда `int`, деление целочисленное |
| `(double) yigindi / n` | 1.6666… | нужное значение |

Ошибка — целочисленное деление `int / int`: хотя `ortacha` (среднее) имеет тип `double`, правая часть сначала вычисляется как целое (*yigindi* — сумма). Исправленная программа:

```python
n = int(input())
a = list(map(int, input().split()))

yigindi = sum(a)
ortacha = yigindi / n                  # в Python / — всегда вещественное деление
print(f"{ortacha:.2f}")
```
```java
import java.util.Scanner;

public class Main {
    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        int n = in.nextInt();
        int yigindi = 0;
        for (int i = 0; i < n; i++) yigindi += in.nextInt();

        double ortacha = (double) yigindi / n;     // сначала в double, потом деление
        System.out.printf("%.2f%n", ortacha);
    }
}
```
```cpp
#include <cstdio>
#include <iostream>
#include <vector>
using namespace std;

int main() {
    int n;
    cin >> n;
    vector<int> a(n);
    for (int i = 0; i < n; i++) cin >> a[i];

    long long yigindi = 0;
    for (int i = 0; i < n; i++) yigindi += a[i];
    double ortacha = (double) yigindi / n;     // сначала в double, потом деление
    printf("%.2f\n", ortacha);
    return 0;
}
```

Для `3` и `1 2 2` теперь выводится `1.67`. В Python этой ошибки нет: `/` — всегда вещественное деление, а целочисленное — `//`. В Java и C++ это одна из самых частых ошибок — поэтому так полезно смотреть в окне Watch **промежуточные выражения** (`yigindi / n`) отдельно.

## Разобранный пример 2: отладочный вывод и assert

Дано *n* (2 ≤ *n* ≤ 10¹²). Выведите его простые множители по возрастанию. Программа записывает каждый шаг в **поток ошибок** — это не влияет на основной вывод — и в конце проверяет результат через `assert`: произведение множителей обязано быть равно *n*.

```python
import sys

n = int(input())
qoldiq = n
kopaytuvchilar = []
d = 2
while d * d <= qoldiq:
    while qoldiq % d == 0:
        kopaytuvchilar.append(d)
        qoldiq //= d
        print(f"[debug] {d} найден, осталось {qoldiq}", file=sys.stderr)
    d += 1
if qoldiq > 1:
    kopaytuvchilar.append(qoldiq)

kopaytma = 1
for p in kopaytuvchilar:
    kopaytma *= p
assert kopaytma == n, "неверные множители"

print(*kopaytuvchilar)
```
```java
import java.util.ArrayList;
import java.util.List;
import java.util.Scanner;

public class Main {
    public static void main(String[] args) {
        long n = new Scanner(System.in).nextLong();
        long qoldiq = n;
        List<Long> kopaytuvchilar = new ArrayList<>();
        for (long d = 2; d * d <= qoldiq; d++) {
            while (qoldiq % d == 0) {
                kopaytuvchilar.add(d);
                qoldiq /= d;
                System.err.println("[debug] " + d + " найден, осталось " + qoldiq);
            }
        }
        if (qoldiq > 1) kopaytuvchilar.add(qoldiq);

        long kopaytma = 1;
        for (long p : kopaytuvchilar) kopaytma *= p;
        assert kopaytma == n : "неверные множители";   // включается через java -ea

        StringBuilder sb = new StringBuilder();
        for (long p : kopaytuvchilar) {
            if (sb.length() > 0) sb.append(' ');
            sb.append(p);
        }
        System.out.println(sb);
    }
}
```
```cpp
#include <cassert>
#include <iostream>
#include <vector>
using namespace std;

int main() {
    long long n;
    cin >> n;
    long long qoldiq = n;
    vector<long long> kopaytuvchilar;
    for (long long d = 2; d * d <= qoldiq; d++) {
        while (qoldiq % d == 0) {
            kopaytuvchilar.push_back(d);
            qoldiq /= d;
            cerr << "[debug] " << d << " найден, осталось " << qoldiq << endl;
        }
    }
    if (qoldiq > 1) kopaytuvchilar.push_back(qoldiq);

    long long kopaytma = 1;
    for (long long p : kopaytuvchilar) kopaytma *= p;
    assert(kopaytma == n);                     // в Release (NDEBUG) отключается

    for (size_t i = 0; i < kopaytuvchilar.size(); i++) {
        if (i > 0) cout << ' ';
        cout << kopaytuvchilar[i];
    }
    cout << endl;
    return 0;
}
```

Для `360` основной вывод — `2 2 2 3 3 5`. В потоке ошибок видны шаги:

```text
[debug] 2 найден, осталось 180
[debug] 2 найден, осталось 90
[debug] 2 найден, осталось 45
[debug] 3 найден, осталось 15
[debug] 3 найден, осталось 5
```

В Visual Studio поток ошибок виден в окне консоли вместе с основным выводом, а автоматическая проверка сравнивает только основной поток (*kopaytuvchilar* — множители, *qoldiq* — остаток, *kopaytma* — произведение). Если условие `assert` не выполняется, программа останавливается с сообщением, и сразу ясно, что ошибка именно здесь. В Java `assert` по умолчанию выключен — он включается командой `java -ea Main`; в C++ он отключается в конфигурации Release из-за `NDEBUG`. Поэтому внутри `assert` не пишут действий, влияющих на работу программы.

:::warning
**Частые ошибки**

- **Игнорирование предупреждений.** Предупреждение вроде «variable used without being initialized» — часто настоящая ошибка; собирайте с `/W4` и исправляйте их.
- **Попытка отлаживать в Release.** Из-за оптимизации переменные «исчезают», а шаги прыгают; для отладки выбирайте Debug.
- **Отладочные `print` в основном выводе.** Автоматическая проверка считает их неверным ответом; используйте `cerr`, `System.err`, `sys.stderr` или удаляйте их.
- **Важное действие внутри `assert`.** `assert(++k < n)` в Release вообще не выполняется, и поведение программы меняется.
:::

:::tip
Найдя ошибку, сохраните вызвавший её ввод как тест. После каждого исправления запускайте все сохранённые тесты заново — так старая ошибка не вернётся.
:::

## Итоги

- IDE объединяет редактор, систему проектов, сборщик, список ошибок и отладчик.
- В Visual Studio работа организуется в решении (`.sln`) и проектах; стандарт и уровень предупреждений задаются в свойствах проекта.
- Debug — для отладки (без оптимизации, `assert` работает), Release — для пользователей.
- Отладчик: точка останова (F9), Step Over (F10), Step Into (F11), окна Locals, Watch и Call Stack.
- Ошибку ищут систематически: воспроизвести → ожидаемый результат → гипотеза → проверка → исправление.

## Проверьте себя

:::check
Q: Чем Step Over (F10) отличается от Step Into (F11)?
A: Step Over полностью выполняет текущую строку и переходит к следующей; Step Into заходит внутрь функции, вызванной в строке.
Q: Почему отлаживать в конфигурации Release неудобно?
A: Оптимизация переупорядочивает код: переменные не видны, шаги не совпадают с исходным кодом.
Q: Что показывает окно Call Stack?
A: Через какую цепочку функций пришли в текущую точку — кто кого вызвал.
Q: Куда выводить отладочные сообщения, чтобы они не мешали автоматической проверке?
A: В поток ошибок: `cerr`, `System.err` или `sys.stderr`.
Q: Чему равно `x` после `int yigindi = 5, n = 2; double x = yigindi / n;` и почему?
A: 2.0: `yigindi / n` — целочисленное деление, а в `double` результат переводится уже потом.
